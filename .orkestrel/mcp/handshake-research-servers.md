# Reference legacy-server unknown-method behavior, researched 2026-08-20

## Findings

Checked against the released reference-SDK server source, at the last tag in each SDK's initialize-era line (TypeScript SDK `v1.x` branch; Python SDK `v1.29.0`, the newest 1.x release, alongside `2.0.0`, both dated 2026-07-28 per the tag list).

| Implementation | Response to an unrecognized method (e.g. `server/discover`) arriving before `initialize` | Exit / silence? | Citation |
|---|---|---|---|
| `@modelcontextprotocol/sdk` TypeScript server (v1.x) | Answers with a JSON-RPC error, `error.code = ErrorCode.MethodNotFound` (`-32601`), `message: 'Method not found'`. The server has no gate requiring `initialize` to complete first — `Server` registers an `initialize` handler like any other method but enforces no ordering, so an unrecognized method hits the same "no handler registered" path in `protocol.ts` regardless of session state, and the transport sends the error and stays open (`capturedTransport?.send(errorResponse)`). | Neither. No code path closes the connection or exits the process on an unknown method. | [`typescript-sdk` `v1.x` branch, `src/shared/protocol.ts`](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/shared/protocol.ts); [`src/server/index.ts`](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/src/server/index.ts) |
| `mcp` Python server, pre-2.0 (`ServerSession`, v1.29.0) | Answers with a JSON-RPC error, but **not** `-32601`. `ServerSession._received_request` gates every request other than `Initialize`/`Ping` behind an initialization-state check: `if self._initialization_state != InitializationState.Initialized: raise RuntimeError("Received request before initialization was complete")`. That `RuntimeError` (and, independently, a `model_validate` failure on a method name the SDK's request-type union does not recognize) is caught by the same blanket `except Exception` in `_receive_loop`, which unconditionally sends `ErrorData(code=INVALID_PARAMS, message="Invalid request parameters")` — `-32602`, not `-32601` — because the exception handler is fixed to one code regardless of the exception's type or origin. | Neither. The exception is caught and answered; the receive loop continues and the process does not exit. | [`python-sdk` `v1.29.0`, `src/mcp/server/session.py`](https://github.com/modelcontextprotocol/python-sdk/blob/v1.29.0/src/mcp/server/session.py); [`src/mcp/shared/session.py`](https://github.com/modelcontextprotocol/python-sdk/blob/v1.29.0/src/mcp/shared/session.py); [python-sdk releases (v1.29.0, v2.0.0, both 2026-07-28)](https://github.com/modelcontextprotocol/python-sdk/releases) |

Neither reference server exits or goes silent on a pre-`initialize` unknown method; both answer with a JSON-RPC error over stdio. Only the TypeScript SDK server's error carries the JSON-RPC baseline code, `-32601`; the Python SDK server's pre-initialization gate intercepts first and answers `-32602` instead, because its blanket exception handler does not distinguish an unknown-method condition from any other request-validation failure — a fact this source-level check establishes but that neither SDK's documentation states explicitly, so it is asserted here from code, not from a changelog or spec page. This means the client-side documentation quoted in the earlier answer, which describes "a legacy server that exits on an unknown pre-`initialize` request" as one case a dual-era client must tolerate, does not describe either reference server's actual behavior — it can be assumed to describe a third-party or older non-reference server, since a client probing the reference implementations found here would receive an error response, not a closed connection.

**Can a spec-compliant legacy peer be assumed to answer an unknown `server/discover` with an error rather than silence?** Yes for these two reference implementations specifically, on the evidence here — both answer rather than going silent or exiting — but a client cannot assume the error carries `-32601`, since the Python reference server answers `-32602` in this exact scenario, and a client cannot assume every third-party legacy server behaves like either reference implementation, since the spec's own compatibility matrix leaves a modern request against a legacy server's response "implementation-defined."

## Orchestrator reading against the client, 2026-08-20

The fallback condition in the MCPClient negotiation catch fires on any discover failure except an MCPError carrying MCP_UNSUPPORTED_VERSION, with no code test, so the Python reference server-s -32602 answer and the TypeScript reference server-s -32601 answer both trigger the legacy fallback, and silence is bounded by the caller-s own request deadline. No client change follows from this research; it corroborates the Q2 ruling and feeds the guide-s worst-case sentence.
